# 코딩을 몰라도 시작하는 첫 게임 만들기

> BASS 0.5와 ChatGPT 데스크톱 앱의 Codex를 이용하는 완전 초보자용 가이드

- 대상: 개발, 터미널, Git, GitHub를 처음 접하는 사람
- 목표: 작은 브라우저 게임을 기획하고, 실제로 실행해 보고, 고치고, 안전하게 저장하기
- 문서 기준: BASS `0.5.0`, 2026-08-19

이 문서는 코드를 외우게 하는 교재가 아니다. 친구가 게임의 감독과 첫 번째 플레이어가 되고, Codex가 개발 작업을 수행하며, BASS가 그 작업이 엉뚱한 방향으로 새거나 확인 없이 끝나지 않도록 관리하게 만드는 사용 설명서다.

처음에는 이 문서의 본문만 읽으면 된다. Node.js, 패키지 인증, BASS 설치 명령은 맨 뒤의 [설치 도우미용 부록](#부록-a-설치-도우미용-최초-1회-준비)에 따로 모아 두었다.

가장 빠른 읽기 경로는 다음과 같다.

- 준비된 폴더를 받은 친구: 1~18장을 순서대로 읽고, GitHub가 필요할 때 19~20장을 읽는다.
- 다음 날 다시 시작하는 친구: [21장](#21-작업을-멈추고-다시-시작하기)과 [25장](#25-한-장짜리-대화-순서)을 본다.
- 환경을 준비하는 도우미: 본문의 원칙을 읽은 뒤 [부록 A](#부록-a-설치-도우미용-최초-1회-준비)를 실행한다.

## 1. 30초 만에 이해하기

게임 개발은 어려운 코드를 많이 입력하는 행위만을 뜻하지 않는다. 다음 순서를 반복해 원하는 경험을 만드는 일이다.

```text
아이디어 말하기
→ 무엇을 만들지 정하기
→ 아주 작은 첫 버전 만들기
→ 직접 플레이하기
→ 불편한 점을 구체적으로 말하기
→ 수정 결과를 다시 확인하기
→ 승인하고 저장하기
```

친구가 맡을 일은 네 가지다.

1. 어떤 게임을 원하는지 자기 말로 설명한다.
2. Codex가 제안한 선택지 중 하나를 고른다.
3. 만들어진 게임을 직접 플레이한다.
4. 만족했을 때만 최종 승인한다.

코드 작성, 터미널 명령, BASS 작업 기록과 검사는 Codex가 맡는다.

## 2. 누가 무엇을 하나

| 역할 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 나 | 재미의 방향, 포함할 기능, 위험한 결정, 최종 승인 | 코드를 이해한 척하거나 검사 없이 승인하기 |
| Codex | 파일 조사, 계획, 구현, 실행, 테스트, 쉬운 말로 보고 | 제품 방향을 대신 확정하거나 스스로 최종 승인하기 |
| BASS | 작업 범위, 시도 횟수, 검사, 근거, 리뷰 상태를 관리 | 게임 아이디어를 대신 선택하거나 외부 도구를 몰래 설치하기 |
| Git | 컴퓨터 안에서 프로젝트의 저장 지점과 변경 이력을 관리 | 인터넷에 자동 업로드하기 |
| GitHub | Git 프로젝트를 온라인에 보관하고 공유 | 코드를 올렸다는 이유만으로 게임을 자동 공개하기 |

쉽게 비유하면 다음과 같다.

- 나는 게임 감독이자 최종 검수자다.
- Codex는 개발팀이다.
- BASS는 제작 일정표, 체크리스트, 작업 일지를 합친 감독 장치다.
- Git은 되돌아갈 수 있는 저장 지점이다.
- GitHub는 저장 지점을 보관하고 다른 사람과 나누는 온라인 공간이다.

## 3. 개발이란 무엇인가

컴퓨터 게임은 여러 파일에 적힌 정확한 지시를 컴퓨터가 실행한 결과다. 예를 들어 다음 문장도 훌륭한 개발 요구사항이다.

> 플레이어가 스페이스바를 누르면 캐릭터가 한 번만 점프한다. 장애물에 닿으면 게임이 끝나고, 다시 시작 버튼이 나타난다.

Codex는 이런 문장을 코드와 화면으로 바꾼다. 하지만 “재미있게 만들어 줘”처럼 기준이 없는 말만으로는 무엇이 성공인지 알 수 없다. 개발에서 가장 중요한 능력은 코드를 외우는 것이 아니라 다음을 분명하게 말하는 것이다.

- 플레이어가 무엇을 하는가?
- 왜 그 행동을 반복하는가?
- 언제 이기고 언제 지는가?
- 지금 만들 기능과 나중에 만들 기능은 무엇인가?
- 내가 직접 해 보니 어디가 불편했는가?

## 4. 꼭 필요한 말만 익히기

### 게임과 프로그램

| 말 | 아주 쉬운 뜻 |
|---|---|
| 프로젝트 | 한 게임을 이루는 파일 전체가 든 폴더 |
| 저장소(repository) | 변경 이력까지 추적하는 프로젝트 폴더 |
| 코드 | 컴퓨터가 따라야 할 행동을 적은 글 |
| UI | 버튼, 점수, 메뉴처럼 사람이 보고 조작하는 화면 |
| 런타임·게임 엔진 | 게임의 화면, 입력, 소리, 물리 등을 실행하도록 돕는 기반 도구 |
| 의존성·패키지 | 프로젝트가 가져다 쓰는 외부 코드 묶음 |
| 버그 | 의도한 것과 실제 동작이 다른 문제 |
| 테스트 | 정해 둔 동작이 계속 맞는지 자동 또는 수동으로 확인하는 일 |
| 빌드 | 여러 개발 파일을 실행하거나 배포할 수 있는 결과물로 만드는 일 |
| 로컬 서버 | 내 컴퓨터에서만 게임을 열어 보기 위해 잠시 켜는 프로그램 |
| URL | 브라우저에서 게임을 여는 주소. 로컬 URL은 보통 내 컴퓨터에서만 열린다. |
| 터미널 | 글로 명령을 입력해 컴퓨터 도구를 실행하는 창 |

### Git과 GitHub

Git과 GitHub는 같은 것이 아니다. [GitHub 공식 입문 문서](https://docs.github.com/en/get-started/learning-to-code/getting-started-with-git)도 Git을 변경을 추적하는 버전 관리 도구, GitHub를 Git 프로젝트를 온라인에 저장하고 협업하는 서비스로 구분한다.

| 말 | 아주 쉬운 뜻 |
|---|---|
| Git | 내 컴퓨터에서 파일 변경 이력을 관리하는 도구 |
| commit(커밋) | “여기까지는 괜찮다”라고 남기는 이름 붙은 저장 지점 |
| branch(브랜치) | 안정된 버전을 건드리지 않고 실험하는 별도 작업선 |
| GitHub | 저장소를 온라인에 보관하고 공유하는 서비스 |
| push(푸시) | 내 컴퓨터의 커밋을 GitHub로 올리는 일 |
| pull·clone | GitHub의 프로젝트를 내려받거나 최신 상태로 맞추는 일 |
| pull request | 한 작업선의 변경을 검토한 뒤 다른 작업선에 합치자고 제안하는 절차 |
| deploy(배포) | 다른 사람이 실제 주소로 게임을 실행할 수 있게 공개하는 일 |

다음 네 가지는 서로 다른 행동이다.

```text
파일 수정 ≠ 커밋 ≠ GitHub 푸시 ≠ 게임 배포
```

- 파일을 수정했다고 저장 지점이 자동으로 생기지 않는다.
- 커밋했다고 GitHub에 자동으로 올라가지 않는다.
- GitHub에 올렸다고 플레이 주소가 자동으로 생기지 않는다.
- 게임 저장소를 GitHub에 올리는 일은 첫 로컬 게임을 만든 뒤로 미뤄도 된다.
- 다만 현재 BASS 패키지 인증에는 패키지 접근 권한이 있는 GitHub 계정이 필요할 수 있으며, 이 준비는 설치 도우미가 맡는다.

## 5. BASS가 뒤에서 하는 일

BASS는 친구가 명령어를 외워서 조작하는 프로그램이 아니다. 친구는 자연어로 말하고, Codex가 내부 작업을 BASS 규칙에 맞게 처리한다.

프로젝트의 주요 문서는 다음과 같다.

| 파일·폴더 | 뜻 | 초보자가 직접 편집해야 하나? |
|---|---|---|
| `PRODUCT.md` | 누구를 위한 어떤 게임인지, 무엇을 넣고 뺄지 | 아니요. Codex와 대화로 결정한다. |
| `TECH.md` | 어떤 기술을 왜 쓰는지, 어떻게 검사할지 | 아니요. 이해할 수 있게 설명만 받는다. |
| `DESIGN.md` | 화면 분위기, 색, 글자, 조작 피드백의 기준 | 취향과 방향만 결정한다. |
| `AGENTS.md` | Codex가 이 프로젝트에서 지켜야 할 규칙 | 직접 지우거나 덮어쓰지 않는다. |
| `bass.yaml` | BASS 버전과 프로젝트 설정 | 도우미 또는 Codex가 관리한다. |
| `.bass/tasks/` | 한 번에 처리할 작은 작업의 명세 | Codex가 관리한다. |
| `.bass/evidence/` | 검사 결과, 화면 확인 등 완료 근거 | 필요할 때 결과만 확인한다. |
| `.bass/records/` | 승인까지 끝난 작업 기록 | Codex가 관리한다. |

BASS 상태가 화면에 보이면 이렇게 읽으면 된다.

| 상태 | 쉬운 뜻 |
|---|---|
| `CAPTURED` | 무엇을 할지 적어 둔 상태 |
| `ACTIVE` | 지금 만들고 확인하는 상태 |
| `REVIEW` | Codex의 검사는 끝났고 사람의 플레이 판단이 필요한 상태 |
| `DONE` | 사람이 승인했고 기록까지 끝난 상태 |
| `NEEDS_DECISION` | 취향, 범위, 위험처럼 사람이 골라야 진행되는 상태 |
| `NEEDS_EXPERT` | 결제, 보안, 법률, 복잡한 서버처럼 전문가 확인이 필요한 상태 |
| `BLOCKED`·`FAILED` | 안전하게 멈춘 상태. 프로젝트 전체가 망가졌다는 뜻은 아니다. |

## 6. 첫 게임의 크기를 작게 잡기

첫 목표는 “완성형 상업 게임”이 아니라 “처음부터 끝까지 플레이할 수 있는 작은 게임”이다. 이것을 첫 플레이 가능 버전이라고 부르자.

첫 게임으로 권하는 범위는 다음과 같다.

- 브라우저에서 실행되는 2D 게임
- 한 문장으로 설명할 수 있는 규칙
- 이동, 클릭, 드래그 같은 핵심 조작 한 가지
- 3~5분 안에 한 판이 끝남
- 승리 또는 목표 한 가지
- 실패 조건 한 가지
- 다시 시작 기능
- 점수나 남은 시간처럼 현재 상태를 보여 주는 표시

첫 버전에서는 다음을 빼는 편이 좋다.

- 온라인 멀티플레이
- 회원가입과 로그인
- 결제, 광고, 가상화폐
- 채팅과 사용자 제작 콘텐츠
- 서버와 데이터베이스
- 수십 개 스테이지
- PC, 모바일 앱, 콘솔 동시 출시
- 사실적인 대형 3D 세계

작게 시작하는 것은 꿈을 포기하는 일이 아니다. 재미의 핵심을 빨리 실제로 만져 보기 위한 방법이다.

## 7. 시작 전에 준비되어 있어야 하는 것

가장 편한 방법은 설치 도우미가 최초 한 번만 환경을 준비해 주는 것이다. 친구의 컴퓨터에는 다음이 있어야 한다.

- ChatGPT 데스크톱 앱과 로그인된 계정
- 사용할 수 있는 Codex 화면
- BASS 플러그인이 설치된 새 세션
- BASS가 연결된 별도의 게임 프로젝트 폴더
- 인터넷 연결

게임 프로젝트를 보관할 GitHub 저장소는 나중에 온라인 백업이나 공유를 시작할 때 만들어도 된다. 다만 현재 BASS 패키지를 내려받기 위한 GitHub Packages 계정과 인증은 최초 설치 단계에서 필요할 수 있다.

준비된 프로젝트 폴더에는 최소한 다음 파일이 보여야 한다.

```text
AGENTS.md
bass.yaml
PRODUCT.md
TECH.md
DESIGN.md
.bass/
```

친구에게 BASS 자체의 소스 저장소를 게임 폴더로 주면 안 된다. `bass-platform`과 친구의 게임은 서로 다른 프로젝트여야 한다.

환경 준비를 직접 해야 한다면 먼저 [설치 도우미용 부록](#부록-a-설치-도우미용-최초-1회-준비)을 함께 볼 사람을 구하는 것을 권한다. 특히 GitHub Packages 인증 토큰은 초보자가 대화창에 붙여넣으며 해결할 문제가 아니다.

## 8. 프로젝트 폴더 열기

ChatGPT 데스크톱 앱은 컴퓨터의 폴더를 로컬 프로젝트로 열 수 있다. [공식 데스크톱 앱 안내](https://learn.chatgpt.com/docs/app)에 따르면 앱에 로그인한 뒤 작업 위치로 폴더를 선택하고, Codex에서 새 대화를 시작하면 그 폴더의 파일을 문맥으로 사용할 수 있다.

1. ChatGPT 데스크톱 앱을 연다.
2. 준비된 게임 폴더를 연다.
3. Codex를 선택한다.
4. 새 대화를 시작한다.
5. 아래 문장을 그대로 보낸다.

```text
이 폴더는 BASS로 관리하는 내 첫 게임 프로젝트야.
나는 코딩, 터미널, Git을 전혀 모르는 초보자야.

- 먼저 AGENTS.md, bass.yaml, PRODUCT.md, TECH.md, DESIGN.md와 현재 BASS 상태를 확인해줘.
- BASS 작업, 명령, 상태 전환, 검증 근거(evidence)와 기록은 네가 내부적으로 관리해줘.
- 개발 용어가 나오면 바로 뒤에 쉬운 뜻을 붙여줘.
- 내가 결정해야 하는 제품 방향이나 위험만 한 번에 하나씩 질문해줘.
- 파일 삭제, 외부 서비스 연결, 결제, push, 배포는 내 명시적 승인 전에는 하지 마.
- 지금은 파일을 수정하지 말고 준비 상태와 다음 한 단계만 5줄 이내로 알려줘.
```

정상이라면 Codex는 프로젝트 파일과 BASS 연결 상태를 조사한 뒤, 무엇을 먼저 정할지 쉬운 말로 알려 준다. 이때 친구에게 `bass task ...` 같은 명령을 직접 입력하라고 계속 요구한다면 다음처럼 바로잡는다.

```text
나는 자연어 사용자야. BASS 내부 명령과 작업 기록은 네가 처리하고, 나는 게임 방향과 최종 결과만 판단할게.
```

## 9. 게임 아이디어 정하기

### 아이디어가 아직 없을 때

다음 문장을 보낸다.

```text
첫 게임 아이디어를 함께 정하고 싶어.
브라우저에서 실행되고, 한 가지 핵심 조작으로 3분 안에 한 판이 끝나는 독창적인 2D 게임 콘셉트 3개를 제안해줘.

각 콘셉트마다 다음만 보여줘.
1. 한 문장 소개
2. 플레이어가 반복하는 행동
3. 승리와 실패 조건
4. 첫 버전에 꼭 필요한 것
5. 첫 버전에서 뺄 것

로그인, 결제, 광고, 멀티플레이, 서버는 제외해줘. 기존 게임의 이름, 캐릭터, 아트, 음악을 복제하지 말아줘. 아직 구현하지 마.
```

마음에 드는 것이 없으면 “2번의 조작은 좋지만 배경을 바닷속 우체국으로 바꿔 줘”처럼 부분만 바꿔 달라고 하면 된다.

### 아이디어가 있을 때

아래 빈칸을 모두 채울 필요는 없다. 아는 것만 쓰고 모르는 것은 `모름`이라고 적는다.

```text
내 게임 아이디어:
- 한 문장 소개:
- 플레이어는 누구인가:
- 가장 자주 하는 행동:
- 목표:
- 실패 조건:
- 한 판 길이:
- 원하는 분위기:
- 꼭 넣고 싶은 것:
- 절대 넣고 싶지 않은 것:
- 모르는 것:

이 아이디어를 첫 게임 크기로 줄여서 선택지와 추천안을 보여줘. 아직 구현하지 마.
```

좋은 한 문장 예시는 다음과 같다.

> 밤의 정원에서 마우스로 색깔이 다른 반딧불을 모아 같은 색 등불에 배달하는 3분 게임. 잘못 배달하면 시간이 줄고, 열 개를 정확히 배달하면 이긴다.

이 한 문장에는 배경, 조작, 반복 행동, 실패의 불이익, 승리 조건이 모두 들어 있다.

## 10. 구현 전에 게임 설계 고정하기

아이디어를 골랐다면 바로 “다 만들어 줘”라고 하지 않는다. 먼저 BASS가 게임 의도와 첫 작업을 문서로 정리하게 한다.

```text
이 콘셉트를 선택할게. 먼저 BASS 방식으로 기획만 구체화해줘.

- PRODUCT.md, TECH.md, DESIGN.md에 필요한 내용만 반영해줘.
- 사실, 내가 결정한 것, 아직 가정인 것, 미정인 것을 구분해줘.
- 첫 플레이 가능 버전을 한 개의 작은 BASS 작업으로 제안해줘.
- 포함할 것과 제외할 것, 조작, 승리·실패 조건, 확인 방법을 쉬운 말로 보여줘.
- 디자인은 기존 작품을 복제하지 않는 독창적인 방향으로 제안해줘.
- 아직 게임 코드는 구현하지 마.
- 내 결정이 필요하면 한 번에 하나씩 물어봐.
```

Codex가 보여 준 계획에서 최소한 다음 여섯 가지에 답할 수 있어야 한다.

1. 플레이어는 무엇을 반복하는가?
2. 조작은 무엇인가?
3. 언제 이기고 지는가?
4. 첫 버전에 들어가는 화면은 몇 개인가?
5. 이번에 만들지 않는 것은 무엇인가?
6. 무엇을 직접 플레이해 보면 완료라고 판단할 수 있는가?

이 중 하나가 명확하지 않다면 구현 전에 고친다. 계획을 바꾸는 비용은 작지만, 이미 만든 게임을 뜯어고치는 비용은 크다.

## 11. 게임 기반 도구 선택하기

런타임 또는 게임 엔진은 게임을 움직이게 하는 기반 도구다. 이름을 외울 필요는 없다. BASS가 2D·3D 여부, 실행 대상, 배포 방식, 기존 도구, 라이선스 위험을 비교하게 하고 사람이 최종 선택하면 된다.

BASS 0.5에는 `vanilla-web`, PixiJS, Phaser, PlayCanvas, Unity 선택지가 있다. 첫 브라우저 2D 게임은 보통 단순한 선택부터 검토하되, 게임에 장면 관리나 물리 기능이 꼭 필요하다면 다른 선택이 더 적합할 수 있다.

먼저 추천만 받는다.

```text
이 게임은 2D이고 웹 브라우저만 대상으로 해. 팀은 게임 엔진 경험이 없고 첫 버전은 최대한 단순해야 해.
BASS 게임 런타임 목록, doctor와 recommend를 이용해 상위 선택지 2개만 비교해줘.

각 선택지가 내 게임에 주는 이점, 새로 생기는 복잡성, 라이선스 위험을 쉬운 말로 설명하고 하나를 추천해줘.
아직 scaffold나 install은 하지 마.
```

추천을 이해하고 동의했을 때만 다음처럼 정확히 승인한다. 대괄호 안은 Codex가 제안한 실제 값으로 바꾼다.

```text
추천한 [런타임 이름]을 선택할게.
프로젝트 내부의 [제안된 경로]에 게임 뼈대를 만들고 필요한 패키지를 설치하는 것을 승인해.
프로젝트 밖 파일, 전역 프로그램, 외부 서비스, push와 배포는 건드리지 마.
충돌이나 예상 밖 변경이 있으면 멈추고 알려줘.
```

이 승인이 필요한 이유는 게임 뼈대 생성과 패키지 설치가 실제 파일을 만들고 인터넷에서 코드를 내려받는 행동이기 때문이다. BASS는 사용자가 고르기 전에 이를 실행하지 않아야 한다.

## 12. 첫 플레이 가능 버전 만들기

계획과 런타임을 골랐다면 다음 문장을 보낸다.

```text
승인한 기획으로 첫 플레이 가능 버전을 구현해줘.

- 시작 전에 BASS 작업의 포함 범위, 제외 범위, 완료 조건을 확정해줘.
- 현재 Git 변경을 먼저 확인하고 기존의 관련 없는 작업을 보존해줘.
- 가장 작은 구현으로 시작해줘.
- 생성된 의존성 폴더와 빌드 결과물이 Git에 들어가지 않도록 Git 제외 목록(.gitignore)을 확인해줘.
- 실제 게임에 맞는 검사와 build를 실행하고, 화면이 있으면 실제 브라우저에서도 확인해줘.
- 작업이 막히면 같은 실패를 반복하지 말고 쉬운 말로 선택지를 알려줘.
- 내가 직접 플레이하기 전에는 최종 승인이나 DONE 처리를 하지 마.
- commit, push, 배포는 하지 마.

준비가 끝나면 실제 실행 주소, 조작법, 확인한 항목, 남은 한계를 알려줘.
```

작업 중에는 Codex가 짧은 진행 상황을 알려 줄 수 있다. 여러 새 요구를 중간에 계속 추가하면 작업 범위와 완료 기준이 흔들린다. 떠오른 아이디어는 “다음 작업 후보로 메모만 해 줘. 지금 작업에는 넣지 마”라고 말한다.

## 13. 권한 요청을 읽는 법

Codex가 명령을 실행하기 전에 허용 여부를 물을 수 있다. 이것은 게임의 최종 승인과 다른, 컴퓨터 행동에 대한 허용이다.

첫 게임에서 예상할 수 있는 요청은 다음과 같다.

- 프로젝트 폴더 안의 파일 읽기와 수정
- 선택한 패키지 설치
- 테스트와 build 실행
- 내 컴퓨터에서 로컬 서버 실행
- 브라우저로 로컬 게임 확인

다음 요청은 이유와 대상을 이해하기 전까지 허용하지 않는다.

- 프로젝트 폴더 밖의 파일 수정 또는 삭제
- 많은 파일을 한꺼번에 삭제
- 전역 프로그램 설치
- 비밀번호, 토큰, 인증서, 개인 파일 읽기
- GitHub push, 저장소 공개 전환, 배포
- 유료 API나 유료 호스팅 연결
- 외부 사람에게 메시지 전송

모르겠다면 거절해도 된다. 그런 다음 이렇게 묻는다.

```text
이 권한이 왜 필요한지, 정확히 무엇이 바뀌는지, 허용하지 않으면 어떤 대안이 있는지를 초보자도 이해하게 세 문장으로 설명해줘.
```

## 14. 직접 플레이하고 확인하기

Codex가 코드를 만들었다고 게임이 완성된 것은 아니다. 반드시 실제 주소를 열어 직접 해 본다.

서버가 아직 켜지지 않았다면 다음처럼 말한다.

```text
게임을 실행하고 실제로 접속되는지 확인해줘. 브라우저에서 열 실제 URL과 조작법을 알려줘. 포트 번호를 추측하지 말고 실행 결과를 확인해줘.
```

`http://localhost:5173`과 비슷한 주소가 나올 수 있지만 번호는 달라질 수 있다. `localhost` 주소는 보통 그 컴퓨터에서 서버가 켜져 있는 동안만 열린다.

첫 플레이에서는 다음을 확인한다.

- 시작 화면이나 게임 화면이 열린다.
- 조작을 눌렀을 때 바로 반응한다.
- 설명을 오래 읽지 않아도 목표를 알 수 있다.
- 점수, 시간, 생명 등 중요한 상태가 보인다.
- 실제로 이기거나 목표를 달성할 수 있다.
- 실제로 실패할 수 있다.
- 끝난 뒤 다시 시작할 수 있다.
- 글자가 잘리고 버튼이 화면 밖으로 나가지 않는다.
- 색만으로 성공과 실패를 구분하게 만들지 않았다.
- 소리를 끄더라도 결과를 이해할 수 있다.

Codex의 자동 테스트가 통과해도 “재미있는가”, “조작감이 자연스러운가”, “규칙이 바로 이해되는가”는 사람이 판단해야 한다.

## 15. 좋은 피드백을 주는 공식

다음 네 가지 순서로 말하면 수정 성공률이 높아진다.

```text
어디에서 → 무엇을 했더니 → 실제로 어떻게 됐고 → 어떻게 되길 원하는지
```

예를 들어 “점프가 이상해”보다 다음 문장이 낫다.

> 첫 장애물 앞에서 스페이스바를 한 번 눌렀는데 캐릭터가 두 번 점프했다. 한 번 누르면 한 번만 점프하게 해 줘. 게임 진행을 막으니 가장 먼저 고쳐 줘.

화면 문제는 스크린샷을 첨부하고 위치를 설명한다.

```text
첨부한 화면에서 오른쪽 위 점수 글자가 잘려 보여.
창 크기가 작아져도 점수 전체가 보이게 해줘.
이번에는 이 문제만 BASS 작업으로 처리하고, 다른 디자인은 바꾸지 마.
수정 후 같은 크기의 화면에서 다시 확인해줘.
```

막연한 취향도 관찰 가능한 말로 바꿀 수 있다.

| 막연한 말 | 더 좋은 말 |
|---|---|
| 더 재밌게 | 첫 30초 안에 위험이 없어서 지루하다. 10초 안에 첫 선택이 나오게 해 줘. |
| 더 예쁘게 | 배경과 버튼의 밝기가 비슷해 시작 버튼이 안 보인다. 주 행동만 더 눈에 띄게 해 줘. |
| 어렵게 | 첫 20초는 유지하고, 이후 장애물 등장 간격만 서서히 줄여 줘. |
| 부드럽게 | 방향을 바꿀 때 즉시 꺾여서 딱딱하다. 0.1초 정도 속도가 변하게 해 줘. |
| 뭔가 이상해 | 두 번째 판을 시작하면 이전 점수가 남아 있다. 재시작 시 0점이 되어야 한다. |

한 번에 한 가지 결과를 요구하는 것이 좋다. 조작, 난이도, 화면 전체, 음악, 새 스테이지를 한꺼번에 바꾸면 어떤 변경이 좋아졌고 어떤 변경이 문제를 만들었는지 알기 어렵다.

## 16. 수정 작업 요청하기

직접 플레이한 피드백은 새 작업으로 분리한다.

```text
아직 최종 승인하지 않을게.
직접 플레이해서 다음 문제를 확인했어.

- 상황:
- 내가 한 행동:
- 실제 결과:
- 원하는 결과:
- 중요도:

현재 BASS 작업의 상태와 Git 변경을 확인한 뒤, 이 문제만 처리할 가장 작은 작업을 제안하고 구현해줘.
기존에 잘 되던 조작과 관련 없는 화면은 바꾸지 마.
수정 후 필요한 검사와 실제 브라우저 확인 결과를 보여줘.
```

오류 문구가 보이면 요약해서 다시 쓰지 말고 전체 문구를 복사하거나 화면을 첨부한다. 파일 경로나 개인 정보가 포함됐는지 먼저 확인한다.

## 17. 만족했을 때만 최종 승인하기

권한 요청에서 “허용”을 눌렀거나 자동 검사가 통과한 것은 게임 결과에 대한 최종 승인이 아니다.

만족하지 않았다면 이렇게 말한다.

```text
아직 제품 결과를 승인하지 않아. 현재 상태를 REVIEW로 유지하고, 내가 확인하지 못한 항목과 남은 문제를 알려줘.
```

직접 플레이했고 완료 조건을 만족했을 때만 다음처럼 말한다.

```text
내가 직접 플레이해서 시작, 핵심 조작, 승리·실패, 재시작을 확인했어.
현재 REVIEW 작업의 완료 조건에 만족하므로 이 작업을 최종 승인해.
BASS에 내 승인을 기록하고 마무리(finalize)한 뒤, 무엇이 DONE이 되었는지와 남아 있는 다음 작업 후보를 쉬운 말로 요약해줘.
```

일부만 확인했다면 확인한 부분을 정확히 말하고 완료 처리는 보류한다. Codex가 사용자의 뜻을 추측해 스스로 승인하게 해서는 안 된다.

## 18. Git으로 안전한 저장 지점 만들기

하나의 플레이 가능한 단계가 승인되면 커밋을 만든다. 친구가 Git 명령을 외울 필요는 없지만, 무엇이 저장되는지는 확인해야 한다.

```text
승인된 현재 작업을 Git 저장 지점으로 남길 준비를 해줘.

1. 현재 변경 파일을 쉬운 말로 설명해줘.
2. 이 작업과 관련 없는 기존 변경이 있으면 제외해줘.
3. node_modules, dist, 비밀값, 개인 파일이 포함되지 않았는지 확인해줘.
4. 이번 BASS 작업 범위만 커밋해줘.
5. 이해하기 쉬운 커밋 메시지를 사용해줘.
6. push는 하지 마.

완료 후 커밋 식별자와 아직 저장되지 않은 변경을 알려줘.
```

커밋은 유용한 저장 지점이지만 무조건 모든 것을 되돌려 주는 마법 버튼은 아니다. 큰 삭제나 구조 변경 전에는 Codex에게 현재 변경, 되돌리는 방법, 영향을 먼저 설명하게 한다.

## 19. GitHub에 올리기

GitHub는 첫 로컬 게임을 만든 뒤 배워도 늦지 않다. 온라인 백업이나 다른 사람과 코드 협업이 필요할 때 시작한다.

초보자에게는 GitHub Desktop처럼 변경과 커밋을 눈으로 볼 수 있는 앱이 편하다. [GitHub 공식 입문 문서](https://docs.github.com/en/get-started/learning-to-code/getting-started-with-git)도 일반적인 Git 작업에 GitHub Desktop을 사용할 수 있다고 안내한다.

처음 GitHub 저장소를 만들 때는 다음을 지킨다.

- 처음에는 비공개 저장소를 권한다.
- 프로젝트 하나당 저장소 하나를 사용한다.
- 비밀번호나 토큰을 저장소 파일에 넣지 않는다.
- 무엇이 올라갈지 확인하기 전에는 push하지 않는다.
- 공개 전에는 사용한 이미지, 음악, 폰트, 코드의 라이선스를 확인한다.

연결 준비가 끝난 뒤에만 다음처럼 요청한다.

```text
이 프로젝트의 Git 저장소와 GitHub 연결 상태를 읽기 전용으로 확인해줘.
올라갈 커밋, 대상 저장소, 브랜치, 공개 여부를 먼저 보여줘.
비밀값과 생성 파일이 없는지 확인하고, 내가 대상과 범위를 승인하기 전에는 push하지 마.
```

Codex가 대상을 보여 주면 저장소 이름과 공개 여부를 눈으로 확인한 뒤 별도로 push를 승인한다.

## 20. 다른 사람에게 플레이 주소 주기

프로젝트를 GitHub에 올리는 것과 게임을 배포하는 것은 다르다.

| 원하는 것 | 필요한 행동 |
|---|---|
| 내 컴퓨터에서만 플레이 | 로컬 서버 실행 |
| 다른 사람에게 코드 보여 주기 | GitHub에 push하고 권한 공유 |
| 주소를 눌러 바로 플레이 | 별도의 웹 배포 |

정적 브라우저 게임은 정적 웹 호스팅에 배포할 수 있지만, 프로젝트 구조에 따라 설정이 다르다. 배포는 개발 작업과 분리해 요청한다.

```text
이 게임을 다른 사람이 URL로 플레이하게 하고 싶어.
먼저 현재 프로젝트가 서버나 데이터베이스 없는 정적 웹 게임인지 확인해줘.
가능한 배포 방식 2개를 비용, 공개 범위, 설정 난이도, 되돌리기 방법으로 비교하고 하나를 추천해줘.
아직 계정 연결, push, 배포는 하지 마.
```

추천을 고른 뒤에도 대상 저장소, 공개 주소, 비용 발생 여부를 다시 확인하고 명시적으로 승인한다.

## 21. 작업을 멈추고 다시 시작하기

게임 서버만 끄고 파일은 남기고 싶다면 다음처럼 말한다.

```text
파일과 작업 기록은 유지하고, 이 프로젝트의 개발 서버만 종료해줘. 실제로 주소가 더 이상 열리지 않는지도 확인해줘.
```

다음 날 같은 폴더를 열고 새 대화를 시작했다면 다음 문장을 보낸다.

```text
이 프로젝트의 AGENTS.md, bass.yaml, Git 상태와 BASS 상태를 확인해줘.
완료된 작업은 다시 하지 말고, 진행 중인 작업과 사람의 결정이 필요한 항목을 쉬운 말로 요약해줘.
파일은 아직 수정하지 말고 다음 한 단계만 추천해줘.
```

관련 대화를 같은 로컬 프로젝트 아래 나누어 두면 폴더 문맥은 유지하면서 목표별 대화를 깔끔하게 관리할 수 있다. 한 대화에는 가능하면 한 가지 결과만 맡긴다.

## 22. 자주 생기는 문제

### “BASS가 설치되지 않았습니다” 또는 플러그인이 보이지 않는다

새 세션인지 확인한다. 플러그인은 설치 후 새 대화에서 활성화되는 경우가 있다. 그래도 안 되면 설치 도우미에게 BASS 플러그인, GitHub Packages 인증, Node.js 20 이상을 확인해 달라고 한다. 임의로 비슷한 도구로 바꾸지 않는다.

### 명령이 실패했다

```text
같은 명령을 반복하지 말고 실패 원인을 진단해줘.
오류의 핵심, 내 파일에 미친 영향, 가장 안전한 다음 행동을 세 부분으로 설명해줘.
수정은 아직 하지 마.
```

원인을 이해한 뒤 수정이 필요하면 별도로 요청한다.

### 게임 주소가 열리지 않는다

```text
개발 서버가 실제로 실행 중인지, 실제 포트가 무엇인지, HTTP 응답이 오는지 확인해줘. 추측한 주소를 주지 말고 확인된 주소만 알려줘.
```

### Codex는 완료라고 하지만 화면이 마음에 들지 않는다

자동 검사는 취향을 대신하지 못한다. 승인하지 말고 스크린샷과 관찰 내용을 전달한다. BASS 상태는 `REVIEW`에 두면 된다.

### `NEEDS_DECISION`이 나왔다

```text
내가 선택해야 하는 결정을 한 문장으로 말하고, 선택지 2~3개와 추천안, 각 선택의 영향을 쉬운 말로 보여줘. 한 번에 하나만 물어봐.
```

### `NEEDS_EXPERT`가 나왔다

억지로 우회하지 않는다. 결제, 개인정보, 보안, 라이선스, 온라인 서버 등 무엇 때문에 전문가가 필요한지 설명을 받고 도우미와 상의한다.

### 예상하지 못한 파일 삭제가 보인다

추가 작업을 멈추고 다음처럼 말한다.

```text
지금부터 파일을 더 바꾸지 마. 현재 Git 변경과 삭제 파일을 읽기 전용으로 조사하고, 이번 작업이 만든 변경과 기존 변경을 구분해줘. 복구는 내가 범위를 확인한 뒤 승인할게.
```

### GitHub push가 실패한다

인증 정보를 채팅에 붙여넣지 않는다. GitHub Desktop 또는 공식 로그인 흐름을 사용하고, 연결을 끝낸 뒤 Codex에게 상태만 다시 확인하게 한다.

## 23. 안전 규칙

### 절대로 대화창이나 저장소에 넣지 말 것

- 비밀번호
- GitHub PAT 같은 접근 토큰
- 결제 카드 정보
- 주민등록번호나 불필요한 개인정보
- 회사나 타인의 비공개 자료
- 공개 권한이 없는 소스 코드와 자산

비밀값이 필요하다는 말을 들으면 도우미에게 안전한 환경 변수나 비밀 저장소 설정을 부탁한다. 값 자체를 Codex 대화에 붙여넣지 않는다.

### 저작권과 라이선스

- 유명 게임의 캐릭터, 로고, 음악, 맵, UI를 그대로 복제하지 않는다.
- “비슷한 느낌”을 원하면 작품 이름보다 색, 속도, 분위기, 화면 밀도처럼 일반적인 특성을 설명한다.
- 외부 이미지, 음악, 폰트, 코드의 출처와 사용 조건을 기록한다.
- 공개나 판매 전에는 라이선스와 상표 위험을 다시 검토한다.

### 전문가와 상의해야 하는 기능

- 실제 돈 결제, 확률형 유료 상품, 광고 수익
- 어린이 또는 사용자의 개인정보 수집
- 계정, 비밀번호, 채팅, 신고 기능
- 온라인 멀티플레이와 자체 서버
- 위치, 카메라, 마이크, 연락처 사용
- 앱스토어 출시와 법적 고지

첫 게임에서는 이런 기능을 빼는 것이 가장 안전하고 빠르다.

## 24. 권장 7일 연습 코스

하루에 한 가지 결과만 만든다. 시간이 더 걸리면 하루를 늘리면 된다.

| 날 | 목표 | 사람이 확인할 것 |
|---|---|---|
| 1일차 | 콘셉트 3개 비교 후 하나 선택 | 한 문장으로 설명할 수 있는가 |
| 2일차 | PRODUCT·TECH·DESIGN과 첫 작업 확정 | 포함·제외 범위가 분명한가 |
| 3일차 | 첫 플레이 가능 버전 | 시작부터 종료·재시작까지 되는가 |
| 4일차 | 조작감 한 가지 개선 | 입력이 의도대로 느껴지는가 |

| 6일차 | 버그 수정과 자동 검사 | 같은 문제가 다시 생기지 않는가 |
| 7일차 | 최종 플레이, 승인, 커밋 | 직접 확인한 범위만 DONE인가 |

이 과정을 한 번 끝낸 친구는 아직 전문 개발자는 아니지만, 아이디어를 테스트 가능한 게임으로 바꾸고 개발팀과 협업하는 핵심 흐름을 경험한 것이다.

## 25. 한 장짜리 대화 순서

막막할 때는 아래 순서만 따른다.

1. `이 폴더의 BASS와 Git 상태를 확인하고 쉬운 말로 알려줘. 아직 수정하지 마.`
2. `3분짜리 독창적인 2D 브라우저 게임 아이디어 3개를 제안해줘.`
3. `이 아이디어를 선택해. BASS 방식으로 기획만 구체화하고 첫 작업을 제안해줘.`
4. `BASS runtime recommend로 선택지 2개와 추천안을 보여줘. 아직 설치하지 마.`
5. `추천한 런타임과 프로젝트 내부 경로를 선택하고 뼈대 생성(scaffold)과 설치(install)를 승인해.`
6. `첫 플레이 가능 버전을 구현하고 검사해. 내가 플레이하기 전에는 승인하지 마.`
7. `게임을 실행하고 확인된 URL과 조작법을 알려줘.`
8. `직접 해 보니 [상황/행동/실제 결과/원하는 결과]였어. 이 문제만 고쳐줘.`
9. `직접 플레이해 완료 조건을 확인했어. 최종 승인하니 BASS finalize해줘.`
10. `이번 작업 범위만 커밋하고 push는 하지 마.`

## 부록 A. 설치 도우미용 최초 1회 준비

이 부록은 친구 혼자 따라 하는 구간이 아니다. BASS 패키지 접근 권한과 인증, Node.js, Git을 이해하는 사람이 한 번만 준비한다.

### A-1. 준비 원칙

- 친구의 게임은 BASS 소스 저장소와 분리된 새 폴더와 새 Git 저장소로 만든다.
- BASS 0.5 CLI를 실행하는 컴퓨터에는 Node.js 20 이상과 npm이 필요하다.
- 게임이 Node.js 프로젝트가 아니더라도 BASS 때문에 대상 루트에 `package.json`을 만들지 않는다.
- 전역 BASS CLI 설치는 선택이다. 플러그인 launcher는 프로젝트의 `bass.yaml` 버전을 사용한다.
- 외부 capability를 쓰지 않는 첫 프로젝트는 `specification=builtin`, `simplicity=builtin`으로 시작한다.
- 런타임 생성과 설치는 친구가 종류와 프로젝트 내부 경로를 명시적으로 고른 뒤에만 한다.

### A-2. 기본 도구 확인

터미널에서 다음을 확인한다.

```bash
node --version
npm --version
git --version
```

Node.js는 `v20` 이상이어야 한다. 친구가 터미널을 사용할 필요는 없지만 BASS와 웹 게임 개발 도구를 실행하는 컴퓨터에는 필요하다.

### A-3. BASS 패키지 인증

현재 BASS 패키지는 GitHub Packages를 사용한다. 패키지를 읽을 수 있는 GitHub 계정과 `read:packages` 권한의 PAT classic이 필요하다.

```bash
npm login --scope=@offbeat24 --auth-type=legacy --registry=https://npm.pkg.github.com
```

토큰은 터미널의 보이지 않는 비밀번호 입력에만 사용한다. 문서, 대화, 저장소, 스크린샷에 남기지 않는다. 패키지 권한이 없는 계정이라면 저장소 소유자가 먼저 접근 권한을 부여해야 한다.

전역 CLI로 점검하고 싶을 때만 다음을 실행한다.

```bash
npm install -g @offbeat24/bass@0.5.0
bass --version
```

### A-4. Codex에 BASS 플러그인 설치

현재 BASS marketplace를 Codex에 추가한다.

```bash
codex plugin marketplace add offbeat24/bass-platform
```

그다음 ChatGPT 데스크톱 앱의 Plugins 탭에서 `bass`를 설치한다. 설치 후 새 세션을 열고, BASS hook의 내용을 검토한 뒤 신뢰할 때만 승인한다. Codex CLI를 사용한다면 `/plugins`에서 plugin browser를 열 수 있다.

플러그인은 친구가 반복해서 명령을 입력하지 않아도 BASS skills와 launcher를 Codex가 사용할 수 있게 해 준다. 외부 플러그인이나 서비스는 BASS가 대신 설치하지 않는다.

### A-5. 빈 게임 프로젝트에 BASS 연결

`friend-first-game` 같은 별도 빈 폴더를 만든 뒤 그 폴더에서 실행한다.

```bash
bass setup . --name friend-first-game --profiles common,web,game --design --non-interactive --capability specification=builtin --capability simplicity=builtin
```

연결 상태를 확인한다.

```bash
bass doctor
bass doctor --capabilities --host codex
bass agent guide --json
```

다음을 확인한다.

- `bass.yaml`의 버전이 `0.5.0`이다.
- 프로파일이 `common`, `web`, `game`이다.
- `AGENTS.md`의 BASS 관리 블록이 한 번만 존재한다.
- `PRODUCT.md`, `TECH.md`, `DESIGN.md`가 있다.
- `.bass/tasks`, `.bass/records`, `.bass/evidence`가 있다.
- 예상하지 못한 `package.json`이 프로젝트 루트에 생기지 않았다.
- doctor에 선택된 외부 provider의 missing 오류가 없다.

전역 CLI를 설치하지 않았다면, BASS 플러그인이 활성화된 Codex 새 대화에서 다음처럼 요청해도 된다.

```text
이 빈 폴더를 BASS 0.5 프로젝트로 설정해줘.
프로젝트 이름은 friend-first-game이고 profiles는 common, web, game, 디자인 검증은 켜줘.
외부 capability 없이 specification과 simplicity는 builtin을 사용해줘.
setup 후 Codex host doctor를 실행하고 생성·보존·충돌 파일을 보고해줘.
아직 게임 runtime은 만들거나 설치하지 마.
```

### A-6. 최초 Git 저장 지점

Git이 아직 없다면 프로젝트 폴더를 Git 저장소로 만들고 BASS 초기 상태만 저장한다.

```bash
git init
git branch -M main
git status --short
git add .
git commit -m "chore: initialize BASS game project"
```

커밋 전에 `git status`로 비밀 파일과 다른 프로젝트 파일이 포함되지 않았는지 확인한다. Git 사용자 이름이나 이메일 설정이 없다면 도우미가 친구의 실제 계정 기준으로 설정한다.

GitHub 온라인 백업이 바로 필요하다면 GitHub Desktop에서 이 로컬 저장소를 추가한 뒤 비공개 저장소로 게시할 수 있다. 친구의 명시적 동의 없이 공개 저장소로 만들지 않는다.

### A-7. 친구가 런타임을 선택한 뒤

먼저 실제 조건으로 비교한다.

```bash
bass runtime list
bass runtime recommend --dimension 2d --targets web --deployment web
```

친구가 결과와 경로를 명시적으로 선택한 경우에만 다음 흐름을 사용한다. 아래 `RUNTIME_ID`와 `GAME_PATH`를 실제 선택값으로 바꾼다. 예를 들어 경로는 프로젝트 내부의 `game`처럼 지정한다.

```bash
bass runtime doctor RUNTIME_ID --targets web
bass runtime scaffold RUNTIME_ID --destination GAME_PATH --targets web --name friend-first-game --confirm
bass runtime install RUNTIME_ID --path GAME_PATH --confirm
bass runtime verify RUNTIME_ID --path GAME_PATH --targets web
```

생성 후에는 다음을 추가로 확인한다.

- `GAME_PATH/node_modules/`와 `GAME_PATH/dist/`가 Git 추적 대상에서 제외되어 있다.
- 실제 build 명령이 통과한다.
- 테스트가 아직 없다면 “테스트 통과”라고 보고하지 않고, 테스트 없음으로 구분한다.
- `bass.yaml` evaluator가 생겼다면 실제 게임 경로와 명령을 가리킨다.
- 브라우저에서 실제 게임 URL이 열린다.
- 친구가 플레이하기 전에는 BASS 최종 승인을 기록하지 않는다.

### A-8. 인계 체크리스트

- 친구가 ChatGPT 데스크톱 앱에서 정확한 게임 폴더를 열 수 있다.
- 새 Codex 대화에서 BASS 플러그인이 활성화된다.
- 패키지 인증 값이 어떤 프로젝트 파일에도 없다.
- BASS doctor 결과에 막힌 항목이 없다.
- Git의 최초 커밋과 현재 변경 상태가 설명 가능하다.
- GitHub를 쓴다면 저장소 소유자와 공개 여부가 맞다.
- 친구가 본문의 첫 번째 확인 프롬프트를 보낼 수 있다.

## 부록 B. 현재 한계와 기대 수준

- BASS는 별도 웹 콘솔이나 게임 제작 버튼을 제공하지 않는다. 자연어 대화가 사용자 인터페이스다.
- Codex와 BASS는 많은 작업을 대신할 수 있지만 재미, 취향, 위험, 최종 승인은 사람이 맡는다.
- 첫 게임도 계획, 구현, 실제 브라우저 테스트를 거치는 장기 작업이 될 수 있다. 한 문장으로 요청했다고 즉시 완성품이 나오는 것은 아니다.
- BASS는 외부 도구를 자동 설치하거나 없는 기능을 흉내 내지 않는다. 필요한 provider가 없으면 멈추고 알려야 한다.
- 로컬 실행, GitHub 업로드, 실제 배포는 서로 다른 단계이며 각각 확인과 승인이 필요하다.
