# BASS 0.2.1 — NAN Edition architecture

이 문서는 NAN Edition의 설계 설명서다. 설치, 배포와 팀 운영 명령은
[README](../README.md)를 따른다.

## Goals and constraints

NAN Edition은 48시간 안에 주제를 실제 플레이 규칙으로 바꾸고, 사람이 승인한
아이디어를 재현 가능한 prototype과 제출 evidence로 연결한다. 하네스가 게임을
대신 만들거나 특정 엔진을 강제하지 않는다.

- Decision: 주제 분석, concept 비교, hard gate, 사람 승인
- Production: runtime 선택, 작업 소유권, 시간 gate, bounded retry
- Evidence: requirement부터 test/build/license까지의 추적성
- 엔진과 platform API는 adapter 뒤에 격리
- 폐기 가능한 게임 코드보다 재사용되는 harness 계약을 더 엄격하게 보호

## Boundary

```text
NAN Domain
├─ Theme / Concept
├─ Runtime Recommendation
├─ Traceability
├─ Gates / Evidence
└─ RuntimePort
       ↑
Adapters
├─ vanilla-web
├─ pixi-web
├─ phaser-web
├─ playcanvas-web
├─ unity
└─ custom

Web Runtime + capacitor-mobile target → Android / iOS wrapper
```

`src/nan/domain`은 engine, npm, Unity, filesystem, subprocess API를 import하지
않는다. `scripts/check-import-boundaries.mjs`가 이 경계를 CI에서 검사한다.
Adapter만 설치, scaffold, tool doctor, build verify 같은 외부 효과를 수행하고
결과를 `pass`, `fail`, `not-verified`로 반환한다.

## Method

NAN Edition은 다음 순환을 사용한다.

```text
theme → concept → human decision → requirement → scenario → test → evidence
```

이 흐름은 AI 생성 결과를 그대로 신뢰하지 않고 계약, 추적성, 결정적 검증,
회귀 테스트, 기준 보호를 별도 시스템으로 둔다. WikiDocs의
[계약](https://wikidocs.net/376854),
[구조와 격리](https://wikidocs.net/376855),
[추적성과 V-model](https://wikidocs.net/376856),
[검증과 charter 보호](https://wikidocs.net/376857),
[측정과 운영](https://wikidocs.net/376858) 원칙을 반영했다.

단, 해당 사례 자체가 단일 사례(n=1)라는 한계와 48시간 prototype의 성격을
고려한다. Hexagonal boundary와 보호 규칙은 안정적으로 재사용할 harness와
runtime adapter에 엄격히 적용하고, 폐기 가능한 게임 내부 코드는 필요한 만큼만
구조화한다.

## Concept Decision Harness

아이디어는 공간, 핵심 동사, 시스템 반응, 압박, 주제 결합, 시각적 보상의 6개
축으로 설명한다.

모든 concept은 다음 7개 hard gate를 가진다.

- `theme-is-mechanic`
- `one-sentence-playable-loop`
- `representative-scene`
- `vertical-slice-in-six-hours`
- `maximum-two-new-core-systems`
- `visible-player-feedback`
- `shippable-evidence`

Concept 평가는 theme, playability, novelty, feasibility, visual clarity 축의 합계
100점으로 운영한다. 실제 배점은 주제가 공개된 뒤 팀이 승인해 concept 문서에
고정한다. 점수만으로 concept을 확정하지 않으며 모든 hard gate와 `approvedBy`가
필요하다.

## Runtime recommendation model

Runtime 추천은 다음 고정 가중치의 결정적 계산이다.

| Criterion | Weight |
|---|---:|
| Concept fit | 30 |
| Six-hour vertical slice feasibility | 25 |
| Build/test readiness | 15 |
| Team/toolchain readiness | 15 |
| Deployment stability | 10 |
| License risk | 5 |

기본 catalog:

| Adapter | Intended use |
|---|---|
| `vanilla-web` | 작은 Canvas/DOM 규칙 |
| `pixi-web` | Grid, Network, Queue, Drag 중심 2D |
| `phaser-web` | Arena, 이동, 충돌, Spawner 중심 2D |
| `playcanvas-web` | 브라우저 우선 3D |
| `unity` | 복잡한 물리·애니메이션·WebGL·native |
| `capacitor-mobile` | web runtime을 Android/iOS target으로 조합 |

추천은 사람의 선택을 돕는 자문이며 최종 runtime은 사람 승인 후 확정한다.

## RuntimePort

```ts
interface RuntimeAdapter {
  descriptor(): RuntimeDescriptor;
  doctor(context): RuntimeCheckReport;
  scaffold(options): ScaffoldReport;
  install(projectRoot): InstallReport;
  verify(projectRoot, targets): VerificationReport;
}
```

추천은 결정적 100점 rubric이며 최종 선택을 자동화하지 않는다. `certified` 상태는
실행한 검사로만 얻는다. 사람의 risk approval은 미인증 runtime 선택을 허용하지만
검증하지 않은 target의 `not-verified` 상태를 바꾸지 않는다.

`certified`는 runtime과 toolchain이 선택 가능한 상태라는 뜻이다. Target
`pass`는 adapter가 실제 build를 실행해 성공한 경우에만 기록한다. Unity와
mobile native build처럼 project-specific 검증은 evidence가 없으면 계속
`not-verified`다.

## Idempotency

`.bass/nan2026-manifest.json`과 runtime별 manifest는 edition, template/adapter
version, 생성 파일 SHA-256을 가진다. 생성기는 다음 규칙을 지킨다.

1. 파일이 없으면 생성한다.
2. 원하는 내용과 같으면 아무것도 쓰지 않는다.
3. 기존 manifest checksum과 일치하는 관리 파일만 template upgrade한다.
4. checksum이 다르면 사용자 수정으로 보고 보존하며 conflict를 반환한다.

Evidence report는 경로순으로 정렬한 파일 checksum만 사용하고 timestamp를 넣지
않으므로 같은 입력에 같은 checksum을 낸다.

## Charter and retry protection

세션 lock은 gate, acceptance criteria, 세 agent shim의 checksum을 고정한다.
변경하려면 사람이 검토한 뒤 명시적으로 다시 lock해야 한다. 두 번 연속 실패하면
작업은 `BLOCKED`, 네 번째 실패한 재작업은 `NEEDS_HUMAN`이 된다.

## Time gates

| Gate | Required outcome |
|---|---|
| T+6 | Vertical slice |
| T+12 | Full playable loop |
| T+18 | Feature freeze |
| T+30 | Content freeze |
| T+36 | Submission candidate |
| T+42 | Submission lock |

48시간 전체를 개발 시간으로 쓰지 않고 마지막 6시간은 build, 영상, 문서와 제출
복구 buffer로 보호한다.

## Team and agent integration

Codex, Cursor, Claude는 각각 규칙 복사본을 갖지 않는다. 얇은 shim이
`nan/AGENT_WORKFLOW.md`와 `bass compose`의 동일한 원천을 참조한다. 기본 3인
역할은 Product/Director, Gameplay owner, Build/Evidence owner이며 Scene,
Prefab, 공용 설정 같은 충돌 가능 파일은 한 명만 소유한다.

AI 제안, 사람 수정과 승인, 변경 파일, test, playtest, commit, build와 license를
제출 evidence에 남긴다. 수용된 critic finding은 회귀 테스트로 고정하고 trace
registry에 연결한다.

### Harness plugin overlay

- Ouroboros는 theme-to-rule 불확실성이 남은 concept 승인 전에만 interview/seed로
  사용한다. 결정을 BASS concept과 trace에 한 번 반영하며, session lock 뒤에는 평가
  근거를 보탤 수 있어도 보호된 charter를 evolve하지 않는다.
- Ponytail은 playable slice의 구현량을 줄이는 데 사용한다. trace, gate, acceptance,
  evidence, 접근성·보안, 실제 target build 요구는 단순화 대상이 아니다. 기계 검증 뒤
  diff가 계획보다 커졌을 때만 review를 추가한다.

NAN 일정과 제출 조건은 구현 시점의
[NAN 2026 공식 사이트](https://nan2026.nhn.com/)와
[NHN 공식 안내](https://inside.nhn.com/news/957)를 기준으로 검토했다.

주요 AI 도구와 외부 라이선스를 제출 기록에 공개한다.
